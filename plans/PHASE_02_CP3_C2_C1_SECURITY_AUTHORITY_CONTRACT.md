## 1. Authority boundary and repository findings

The frozen CP3-C2-A/B issuer contracts remain issuer-specific. A current `issuer_authority_link_heads` row with `link_state=APPROVED` is a prerequisite, not a Security decision. Its key is **provider identity**, not issuer alone. Every Security candidate binds its exact provider, issuer, immutable approved issuer link, link content hash, and captured issuer head state hash. C3 must compare those values with the current issuer head inside its final writer transaction. A different approved issuer version also invalidates the old binding.

The baseline code has `ShareClass.COMMON` only, `MappingStatus.VERIFIED | UNRESOLVED`, Phase 1 `securities` uniqueness on `(market, exchange, ticker, share_class)`, and a legacy `provider_identity_mappings` partial unique index on one `VERIFIED AND valid_to IS NULL` row per provider. `SQLiteMetadataRepository.list_securities()` reads the Phase 1 table, and the existing provider repository requires that table for a legacy VERIFIED mapping. These tables cannot truthfully represent ticker reuse, distinct common classes sharing a ticker, or revocation without inventing a validity end date. `0005` B evidence, bundle, decision, approval and link tables describe issuer authority and are not Security storage. `0006`/`0007` reviewer crypto/credential/counter primitives may be used by later C3, with distinct Security challenge and event tables. `0001`–`0007` remain byte-identical.

The additive solution is `0008_phase_02_cp3_c2_c_security_authority`: a versioned Security ledger, an immutable canonical Security v2 subject table, immutable profiles/listing history, and one rebuildable current link head. Phase 1 securities and mappings remain historical compatibility data. No 0001–0007 rebuild is proposed. C3 must migrate any *current* application read that claims effective verification to the new head + issuer-head projection before producing new approved links; a Phase 1 fixture row never gains Security authority by migration or relabeling.

| rules / ID | `security-authority-rules/0.1.0`, `security-authority-id/1` |

Contract versions are literal closed tokens; a change to semantic fields or normalization creates a new version. For every content hash: normalize all strings to Unicode NFC, validate closed enum tokens and exact field sets, serialize UTF-8 JSON with lexicographically sorted object keys (Unicode code-point order), no insignificant whitespace, explicit permitted `null`, UTC instants with fixed microsecond precision `YYYY-MM-DDTHH:MM:SS.ffffffZ`, date-only `YYYY-MM-DD`, integers/decimal strings instead of binary floats, and SHA-256 lowercase as `sha256:<64 hex>`. A source field typed date-only is never converted to an instant. Set-valued arrays deduplicate and sort by the contract's specified semantic key; event-chain arrays retain predecessor order. Reject duplicate JSON keys, NaN/Infinity, locale sorting, implicit case folding, and unknown fields. Audit clocks (`fetched_at`, `retrieved_at`, `evaluated_at`, `authenticated_at`, `recorded_at`), database IDs, row/response order, and local paths are excluded from semantic IDs and content hashes; separate audit hashes may include them. Source-supplied effective/listing dates and accepted document identities are semantic **only when explicitly present**. Missing dates are `null` plus a reason, never review/recording time.

Deterministic ID formulas use UTF-8 NFC bytes of the exact anchor string and lowercase SHA-256:

```
KR anchor = security-v1|<issuer_id>|KRX_ISIN|<exact 12-character KRX ISIN>
US anchor = security-v1|<issuer_id>|SEC_REGISTERED_CLASS|<verified registrant CIK>/<accepted accession>/<class-row-id>
security_id = "security_" + sha256(UTF8_NFC(anchor)).lowerhex
```

Anchor components are exact validated values. This version **forbids delimiters** `|` and `/` in component tokens (no caller-provided escaping); issuer ID follows the approved B SafeId, KRX ISIN is 12 uppercase alphanumeric characters with a valid ISIN check digit, registrant CIK is B-verified ten-digit zero-padded CIK, and accepted accession retains its exact SEC `##########-##-######` form. The US `class-row-id` is `sha256:` plus SHA-256 of canonical JSON containing immutable accepted SEC document identity `(verified registrant CIK, accepted accession, filing document digest/form)` and exact registered-class row semantics `(registered class title, Section 12 basis, official in-document class discriminator, registered exchange text if present)`. Exact duplicate semantic rows collapse; distinct rows that cannot be separated by these semantics block as ambiguous. A parser row number, response order, DB row ID, ticker, login/accession-prefix/agent CIK, retrieval time, and provider values are prohibited. The founding anchor and `security_id` never change; an official correction may append a new identifier/profile with explicit same-instrument relation, not rekey the subject.

An OWNER of one field does not own a neighboring field. Positive paths require the named owners **and** supporting bridges; an official document by itself is never sufficient.

Each immutable `security_authority_source_policies` row represents **one** exact `(source_namespace, authority_classification, document_kind, scope, subject_role, policy_version)` admission, not a wildcard. ## 4. Evidence → application → bundle → decision

Evidence is an immutable, source-native fact keyed by document identity, source namespace, document kind, raw digest, exact subject and source-supplied semantic dates. An observation records retrieval/as-of, access result, adapter/parser versions, and raw/source digest without changing evidence identity. Relations append `CORRECTS`, `SUPERSEDES`, or `SAME_INSTRUMENT_CORRECTION` with both evidence IDs and an authority-supplied effective date or explicit null. Applications bind one evidence fact to one exact policy, scope, subject role, provider, proposed issuer/security candidate, claimed weight, taint and disposition (`ADMITTED`, `SUPPORT_ONLY`, `REJECTED`); source facts are not silently promoted by parser output. Identifier, class and listing claims each point to an admitted application and preserve contrary/overlapping claims rather than choosing a winner.

A bundle is an immutable, content-hashed set of exact application IDs **and hashes**, scope results, and current provider observation IDs; bare evidence IDs cannot authorize a decision. It stores provider identity, issuer, captured `issuer_authority_link_id`, immutable issuer `link_content_hash`, `issuer_link_state=APPROVED`, captured head `state_hash`, proposed anchor/ID/profile hash, source policy/rules/freshness versions and collision-scan digest. Bundle membership rows have no duplicates and are sorted by semantic key in bundle hashing. Scope results say `SATISFIED | MISSING | CONFLICT | STALE | UNSUPPORTED`; no `MISSING` becomes zero/empty. Bundle provider-observation membership must be of the same provider and current under the stated freshness policy. An exact `READY_FOR_MANUAL_REVIEW` decision requires all mandatory scope results satisfied, required current observations and a CLEAR collision result. Otherwise machine state is `UNRESOLVED`, `STALE` or `REVIEW_REQUIRED` with explicit reasons. One append-only decision chain per provider has one leaf; a new evaluation references the predecessor. Machine maximum is READY; machine Security writes = 0 and final mapping writes = 0.

The rule registry is `security-authority-rules/0.1.0`; source eligibility and document freshness are repository policies, not claimed by callers. Freshness needs a source-specific as-of/accepted/effective clock plus conservative maximum age where applicable; an absent official clock is `STALE`/`UNRESOLVED`, not fresh from retrieval time. A latest-status, Form 25, correction and collision scan must include later relevant facts, including contrary evidence not selected into the candidate bundle.

## 5. Jurisdiction paths and class model

**KR READY:** exact current approved issuer head and issuer; unique 12-character KRX ISIN/standard-code authority; exactly matching KRX issue-basic row, market and share kind; official current listing status or exact official interval; OpenDART stock-code bridge to that KRX issue; current provider observation whose ISIN equals KRX ISIN; required freshness; global collision CLEAR. An issuer whose legal jurisdiction remains unsupported (including a KRX-listed foreign issuer) cannot be coerced to KR by venue. Missing ISIN, duplicate active ISIN, ambiguous issue rows, missing or unsupported share kind, missing listing evidence, DART bridge mismatch, provider ISIN mismatch, ticker/name-only match, or nonapproved issuer head gives no READY state and no Security/final mapping write. Duplicate active identifiers quarantine **all** affected candidates, including previously approved heads.

**US READY:** current approved issuer head with B-verified registrant CIK; accepted SEC registered-class filing and exact class title/row identity; current field-owning primary-exchange issue/listing row; class/title/ticker/exchange agreement; no effective Form 25 or later contradiction; exact current provider ticker/market bridge; fresh evidence and global collision CLEAR. SEC alone and exchange alone are insufficient. Accession-prefix CIK, login CIK and filing-agent CIK are provenance only; C never resolves a different issuer. Provider CUSIP/ISIN are support/discovery only. `CGS` is disabled without separate license/authorization. If the exchange's official current record is inaccessible, the candidate stays unresolved.

`security_authority_profiles` keeps exact `instrument_family` (`COMMON_EQUITY`, `PREFERRED_EQUITY`, `ADR`, `ETF`, `ETN`, `WARRANT`, `OTHER`, `UNKNOWN`), registered class title or explicit null, authority share kind, identifier kind/value, listing venue/market, source-effective dates and a hash of the owning claims. Initial positive canonical writes are limited to proven `COMMON_EQUITY`. Every other family or unknown class is `UNSUPPORTED`/`UNRESOLVED`, Security write 0, and never coerced to legacy `ShareClass.COMMON`. Two distinct SEC registered classes of common equity get distinct US anchors/subjects/profiles even though a *view-only* legacy projection may label each COMMON. The global Phase 1 enum is unchanged; extending it requires a separate versioning decision. A ticker is mutable listing evidence. Official continuity can append listing/profile history under the same subject; absent continuity creates a new candidate. Ticker reuse never proves identity. A corrected ISIN retains the original Security ID only with explicit KRX same-instrument correction relation; otherwise it is a new candidate and new human review.

## 6. Human disposition, terminal authorization and business transaction

Disposition tokens remain `APPROVED`, `REJECTED`, `REVOKED`, `SUPERSEDED`. Every disposition requires a fresh, single-purpose Security WebAuthn assertion using the frozen R1 cryptographic, credential, counter and OWNER semantics. Security-specific challenges, consumptions and authentication events are separate from issuer disposition tables. The server constructs each challenge from reviewer principal/role (`LOCAL_DATA_STEWARD`), credential/public fingerprint, exact decision and bundle IDs/hashes, provider/issuer/Security subject, expected issuer link/head, disposition, predecessor approval/link, successor decision or explicit null, expiry and 32 OS-CSPRNG challenge bytes. Caller-supplied authenticated booleans or authority fields have no force. Raw assertion secrets are not logged.

**Terminal authentication rule (M1).** One later C3 `BEGIN IMMEDIATE` contains two logical domains. Domain A is outside the business SAVEPOINT: resolve the challenge; check exact binding and expiry; verify WebAuthn signature/origin/RP/UV, credential, OWNER and the **shared** R1 counter graph; append a terminal challenge-consumption row; append a successful Security authentication/counter edge when verification succeeds. A successfully verified assertion and its counter edge remain durable even if the requested disposition later fails. A success authentication event is permitted to have **no** approval event or link: it proves terminal authentication, not business approval. The exact successful consumption and authentication rows are joined by immutable IDs and UNIQUE challenge/credential bindings.

Domain B begins only after successful authentication: `SAVEPOINT security_disposition_business`. Revalidate inside the writer lock the unique current READY decision where required; exact decision/bundle/application/evidence hashes; the exact current APPROVED issuer head for a positive approval; instrument, class, listing, latest contradiction, freshness and global collisions; predecessor approval/link and Security head CAS expectation. Then insert-or-verify canonical v2 subject/profile as applicable, append the human approval event and Security link, guard the head CAS, and assert provider identity/source-history rewrites = 0. C3 writes no legacy VERIFIED row under this proposal. Release the SAVEPOINT and commit the outer transaction on success.

On a post-authentication business failure (changed issuer head, decision leaf, bundle/hash, class/listing, collision, predecessor or CAS), roll back **only Domain B's SAVEPOINT**, commit Domain A, then return/raise a typed business failure **after** the outer transaction has committed. Security subject/profile, approval, link and head business writes are zero from the failed attempt; consumption and successful authentication remain. The same challenge can never be consumed again. The implementation must catch typed business failures at the SAVEPOINT boundary and not let them escape the outer transaction before commit. An unexpected failure that makes Domain A's durable commit impossible is a security/availability failure, not permission to replay an assertion; recovery requires fresh challenge issuance and ledger reconciliation.

**Pre-authentication failure is distinct.** Expiry, signature/origin/RP/UV failure, challenge-binding failure, invalid credential, OWNER failure, and counter/replay rejection follow the approved R1 terminal/rejected-consumption behavior appropriate to that failure. They never fabricate a VERIFIED Security authentication edge or enter Domain B. A post-authentication business failure never changes a VERIFIED authentication to REJECTED. Successful authentication is terminal one-use; successful disposition is a separate fact.

`REJECTED` records one authenticated disposition event only, with no subject/profile/link/head write. `REVOKED` records a fresh authenticated event and REVOKED link/head CAS while preserving the old subject, approval and provider history; it invents no `valid_to`. For `SUPERSEDED`, challenge A authorizes the **old** decision/bundle and disposition `SUPERSEDED`; challenge B authorizes the **successor READY** decision/bundle and disposition `APPROVED`. Both are verified and terminally consumed in Domain A before the pair's business SAVEPOINT. If A succeeds and B fails, A remains consumed; no pair business rows commit. If A and B succeed but the pair business mutation fails, **both** consumptions/authentication counter edges remain durable while both approval events, both links, pair row, canonical/profile changes and head CAS steps roll back. Retry requires two fresh challenges/assertions. Within a successful Domain B the pair row, old SUPERSEDED event/link, successor APPROVED event/link and two guarded head CAS steps (old→SUPERSEDED→successor APPROVED) are atomic; the intermediate head is never committed. Before releasing this SAVEPOINT, perform pair-completeness and `PRAGMA foreign_key_check` checks so a deferred-pair failure is handled as a Domain B failure while A/B authentication remains commit-ready. A deferred COMMIT check is a final backstop, not the ordinary error path.

### 6.1 Exact A/B supersession authorization (M2)

Let current link `L0` reference current approved event `E0`, old decision `D1` with hash `DH1`, old bundle `B1` with hash `BH1`, provider `P`, issuer `I`, and current Security `S1`. Let successor READY decision `D2` with `DH2` bind successor bundle `B2` with `BH2` and proposed Security `S2`. A/B challenges share one server-owned supersession-intent ID and expected `L0/E0` context but are distinct. A's challenge and authentication bind `(P,I,S1,D1,DH1,B1,BH1,SUPERSEDED,E0,L0,expected head state/hash,D2)`; the `D2` field is successor **context**, never A's authenticated decision. B's challenge and authentication bind `(P,I,S2,D2,DH2,B2,BH2,APPROVED,E0,L0,expected issuer APPROVED head,intent)`. B cannot authenticate `D1/B1`; A cannot authenticate `D2/B2`. The pair's business row later binds actual authentication A/B, event/link A/B and the same intent. The successor decision must name `D1` as its direct predecessor for this initial contract; a different lineage is REVIEW_REQUIRED and needs a new explicit design decision rather than an implicit jump.

### 6.2 One R1 signCount history, Security as an additive edge source (M3)

Frozen R1 `reviewer/ledger.py::_counter` currently reconstructs a credential from credential-operation authentication plus issuer `reviewer_authentication_events`. The same algorithm checks credential ID/fingerprints, `counter_capability`, RP/origin and VERIFIED flags; for `SIGN_COUNT_SUPPORTED` it requires a strictly increasing, nonforking chain of `(previous_sign_count, asserted_sign_count)`; for `NO_USABLE_COUNTER` those numeric fields remain null and challenge one-use still applies. R1 crypto verification, counter acceptance, replay and OWNER semantics are **UNCHANGED**.

Before C3 Security authentication can be operational, its read adapter/table registration must add `security_reviewer_authentication_events` to that **same** transaction-scoped R1 ledger input set. Logical input is credential-operation authentication + issuer authentication + Security authentication, with every VERIFIED Security row included even when its business SAVEPOINT rolled back. There is no Security-only counter cursor, independent counter table or second counter truth. Future C3 may add the new table registration and union source to the reader; it must preserve the frozen `_counter` validation algorithm. If that instead requires changing accepted R1 counter rules: **R1 SECURITY CONTRACT CHANGE REQUIRED — STOP**.

Each immutable Security authentication row carries `webauthn_credential_id`, `credential_id_fingerprint`, `public_key_fingerprint`, `counter_capability`, `previous_sign_count`, `asserted_sign_count`, `counter_verified`, `authentication_result` (`VERIFIED` for a successful edge), `rp_id`, `exact_origin`, `authentication_policy_version`, the R1 verification/replay flags, principal/role/OWNER binding, exact challenge and terminal consumption IDs/hashes, and the Security A/B authorization tuple above. Its contract-specific content hash is checked by the common ledger reader before the row contributes an edge. For `NO_USABLE_COUNTER`, previous/asserted are null as in R1; for a VERIFIED supported counter they are integers and satisfy the same strict rule. A Security business failure never removes its accepted edge.

Issuer and Security writers on the same credential acquire `BEGIN IMMEDIATE` before reconstructing this **union**. One writer commits the counter successor first; the second reconstructs the new current count and must reject a stale or duplicate predecessor/asserted count under the existing strict-counter rules, recording the applicable terminal rejection and requiring a fresh challenge/assertion. No accepted fork is possible. This does not strengthen `NO_USABLE_COUNTER` into a numeric counter it does not have.

## 7. Effective mapping, legacy boundary, issuer cascade

Effective mapping is `VERIFIED` only if the Security head for that provider is `APPROVED`, its referenced link/profile/subject are present, the **current** issuer head still equals the link's captured approved issuer authority version and state hash, and no current safety/collision block exists. All other cases are `UNRESOLVED`. A read must fail closed if its head projection is missing/inconsistent. The Security head is the source of truth; no current reader may use legacy `provider_identity_mappings` or Phase 1 `securities` to assert C authority. The later C3 read migration is a required gate, not performed here.

**Legacy decision:** C3 writes **zero** new Phase 1 `ProviderIdentityMapping(VERIFIED)` rows. The 0001 table's `valid_to=NULL` current index and immutable historical meaning make repeated approval/revocation/supersession impossible without a false instrument end date or destructive update. Existing fixture rows remain regression snapshots, identifiable by their existing provider contract/source lineage; they cannot authorize C heads. No old row is silently updated. Logical `ProviderIdentityMapping(VERIFIED)` is a v2 read projection from the Security head, tied exactly to its `security_authority_link_id` and approval event, not a v1 stored row. If a physical v1 VERIFIED row is later required by a consumer, that is a separate explicit compatibility/versioning decision; C3 cannot claim completion while such a consumer still reads v1 current status. A new additive compatibility *view* may be designed later, but is not required by 0008 storage.

Issuer-head loss workflow is per provider, matching B's head key. When an approved B head is about to change link/version/state away from the Security link's captured APPROVED version, the writer starts `BEGIN IMMEDIATE`, discovers every current APPROVED Security head for the affected provider (and, for an issuer-wide action, enumerates **all** approved provider heads for that issuer), appends a `REVIEW_REQUIRED` Security link for each, CASes each Security head, then CASes the issuer head. Old Security, profile, approval, links and provider observations remain. Additive `0008` triggers on B head UPDATE/DELETE abort a loss/change while any affected Security head remains APPROVED; they make an unintegrated old B writer fail closed. A Security effective read also compares the B head, so even an out-of-band inconsistency cannot appear VERIFIED. Issuer-wide mutations must enumerate B heads under the same write lock; no issuer-id-only shortcut can silently leave a provider approved. C3 must integrate this workflow with B writer before operational use; C1 changes no B runtime.

## 8. Collision and race rules

Collision scans read the whole relevant current claim set under the write lock: KRX ISIN, future **licensed** CGS identifier only if separately enabled, SEC registered-class anchor, one provider competing for multiple Security candidates, the same authority class asserted for distinct subjects, and overlapping ticker/listing intervals with unresolved identity. Store contradictory claims; never use a unique claim index to select first writer. A collision marks every affected candidate `REVIEW_REQUIRED`; existing APPROVED links get append-only REVIEW_REQUIRED successors and head CAS in the same evidence publication/decision transaction. A C3 approval reruns the scan just before its CAS. Pending READY decisions become stale through appended successor decisions, not UPDATE. Where claim ingestion cannot atomically suspend affected heads, it must fail closed and not publish the claim as authority. Effective reads independently require collision CLEAR.

SQLite serializes writers with `BEGIN IMMEDIATE`. `APPROVED` vs `REJECTED` on one decision: one initial-disposition unique index winner; the loser's business SAVEPOINT rolls back, but any already VERIFIED authentication remains terminal. Two APPROVED attempts: decision uniqueness plus guarded head insert/CAS gives one business winner. Two mapping successors and REVOKED vs safety transition: unique link predecessor and head CAS permit one committed successor; a loser must re-evaluate with a fresh challenge. SUPERSEDED pair vs competing mapping mutation: one business SAVEPOINT, two distinct durable authentications, one predecessor chain and two guarded CAS steps; no committed partial pair. A late identifier collision is rescanned inside that SAVEPOINT, and affected existing heads are suspended before another positive commit. No retry may reuse a consumed challenge; a new decision/challenge is required after re-evaluation. Strict signCount races across issuer and Security use the single reconstructed R1 edge set described in §6.2.

## 9. Proposed `0008` inventory and relational proof

All IDs are server-derived or server-validated, all FKs use `PRAGMA foreign_keys=ON`, all content/audit hashes are NOT NULL except explicitly optional predecessor/cause, and immutable rows have BEFORE UPDATE/DELETE `RAISE(ABORT)` triggers. `UNIQUE` on a referenced composite key is declared explicitly; SQLite cannot target a merely descriptive index. Composite FK columns are NOT NULL when they are the binding. A CHECK guards nullable alternatives. The supersession-pair FKs to both human events and links are `DEFERRABLE INITIALLY DEFERRED`, so both complete inside one transaction or commit fails. Other FKs are immediate. Insert order is policy → evidence/observations → applications/claims → bundle/members → decision → challenge/consumption/auth → subject/profile → supersession-pair placeholder (only for pair) → approval → links → head.

## 10. Upgrade, downgrade, acceptance and limits

`0008` upgrade order: verify `0007` head; create only additive unique indexes/triggers on B and provider observation tables plus the 23 new tables/indexes/triggers; validate existing rows without rewriting them; keep C writer disabled until C2/C3 gates. A failure rolls back migration atomically. Downgrade is permitted only when **all 0008 authority/history tables are empty**; then drop 0008 triggers/indexes/tables in reverse dependency order. If any C evidence or authority row exists, downgrade aborts and preserves the database. No automatic copying of Phase 1 fixtures into C. Operational backup/recovery and migration test belong to later authorized implementation.

Acceptance gates for C2/C3: exact source access/license/schema admission; canonical JSON deterministic replay; complete KR/US positive and negative matrices; all immutable/relational guards; global collision quarantine; issuer-head safety cascade; terminal consumption surviving one-auth and two-auth post-auth business SAVEPOINT failure; exact D1/B1→D2/B2 pair positive and all swapped/same-auth/wrong-predecessor/partial negatives; Windows-native R1 primitive validation; head/read migration with no stale legacy VERIFIED claim; migration repeat/downgrade test; standard frontend/backend/type/build/secret/Phase acceptance gates. The later shared-counter tests MUST include registration 5 → issuer 5→6 → Security 6→7 → issuer 7→8; Security → credential-lifecycle authentication → Security on one credential; issuer → Security → credential replacement/revocation path, verifying all prior accepted edges remain visible and a revoked/replaced credential cannot authenticate again; an issuer/Security same-predecessor strict-counter race with one accepted successor and one rejected stale assertion; and NO_USABLE_COUNTER null-count behavior without changing R1 rules. Any successful Security authentication followed by business failure must still advance the subsequent current-counter reconstruction. This design's own feasibility check is an **in-memory, disposable SQLite prototype**, not a migration or runtime test. No C2/C3 gate is claimed complete here.

Open / NOT VERIFIED: actual KRX/SEC/primary-exchange current adapter schemas, access and redistribution terms after the frozen CP3-C2-A research date; exact current field coverage for market-specific share kind and US class discriminator; production freshness windows; complete migration DDL against a full migrated database; future C2/C3 integration with B issuer writer, provider readers and Windows WebAuthn; complete business acceptance tests and GPT independent architecture verdict. If official facts changed, the adapter must stop for renewed source research before production admission. CGS remains unavailable. No live calls or credentialed collection occurred in C1.
