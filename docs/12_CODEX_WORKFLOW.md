# Codex Workflow

## 1. 기본 방식

```text
전체 사양 저장
→ Phase별 /plan
→ 계획 검토
→ Phase별 /goal
→ 자체 테스트·QA
→ 별도 채팅 독립 리뷰
→ GPT 통합 QA
→ 버전 태그
→ 다음 Phase
```

---

## 2. `/plan` 사용

복잡하거나 아직 구현 순서가 확정되지 않은 단계는 `/plan`으로 시작한다.

계획은 다음을 포함해야 한다.

- 목표
- 읽을 문서
- 생성·수정 파일
- 단계
- 테스트
- 비범위
- 위험
- 롤백
- 완료기준

계획 승인 전 코드를 수정하지 않는다.

---

## 3. `/goal` 사용

Goal 하나는 Phase 하나만 담당한다.

좋은 Goal:

- 목표가 하나
- 멈춤 조건이 검증 가능
- 변경 금지 범위 명확
- 실행할 테스트 명확
- 진행 로그 산출

나쁜 Goal:

```text
전체 대시보드를 완성하고 자동매매까지 해줘.
```

좋은 예:

```text
Phase 1 Foundation을 구현하고 fixture 기반 계약·테스트·build가 모두 통과할 때 종료한다. 외부 API와 주문 기능은 변경하지 않는다.
```

---

## 4. 진행 중 개입

다음 경우에만 방향을 수정한다.

- 보안 위험
- 사양 충돌
- 외부 API 접근 필요
- 데이터 손상 가능
- 목표 범위 확대 시도
- 완료조건 변경 시도

단순 구현 세부는 Codex가 계획 안에서 처리하게 한다.

---

## 5. 독립 리뷰

구현 채팅과 별도 채팅에서 읽기 전용으로 리뷰한다.

리뷰 항목:

- 요구사항 누락
- 보안
- 계산
- 결측·정정·중복
- 테스트 사각지대
- 하드코딩
- mock을 실데이터로 오인
- 문서와 코드 차이
- 유지보수

리뷰는 파일·줄·테스트 근거를 포함한다.

---

## 6. GPT 통합 QA에 전달할 자료

- 관련 MD
- `git diff`
- Codex 자체 QA
- 독립 리뷰
- 테스트 로그
- 샘플 JSON
- DB schema
- 화면 캡처
- 원문 API 샘플
- Known Issues

---

## 7. Git 방식

```text
main
feature/phase-01-foundation
feature/phase-02-toss
feature/phase-03-dart
feature/phase-04-sec13f
...
```

- 한 Phase 한 브랜치
- 승인 전 main 병합 금지
- 승인 후 태그
- 병렬 작업은 동일 파일을 동시에 쓰지 않음
- 가능하면 worktree 사용

---

## 8. 문서 변경

Codex가 필수 요구사항을 임의 변경하지 않는다.

변경이 필요하면:

1. `DECISIONS.md`에 `PROPOSED`
2. 영향
3. 대안
4. 마이그레이션
5. 롤백
6. 사용자·GPT 승인
7. 사양 변경
8. 코드 구현

---

## 9. 종료 보고

```text
현재 체크포인트
완료한 요구사항
검증 결과
남은 항목
차단사항
다음 권장 작업
```

완료조건 미충족 시 `PARTIAL`로 보고한다.
